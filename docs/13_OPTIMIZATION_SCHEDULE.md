# Optimization Agent — расписание рекомендаций

Рекомендации по оптимизации генерируются **фоном** (BullMQ / inline-очередь),
а не при открытии вкладки «Рекомендации». Специалист видит уже готовый список.

## Когда запускается прогон

| Момент | Триггер | Зачем |
|--------|---------|-------|
| **День 0** | сразу после успешной публикации кампании из платформы | быстрый sanity-check: нулевые конверсии, явный мусор в поисковых запросах |
| **День 7** | `optimization_next_run_at = launched_at + 7 дней` | первое полноценное недельное окно статистики |
| **Далее** | каждые **7 дней** от последнего успешного прогона | регулярный цикл контекстолога без ручного «Обновить» |

Интервал **7 дней** — компромисс для SMB-кабинетов:

- статистика Яндекс/Google стабилизируется за 5–7 суток;
- чаще (1–2 дня) даёт шум и лишние LLM-вызовы;
- реже (14–30 дней) пропускает просадку CTR/CPL.

Константа `OPTIMIZATION_RECURRING_DAYS` в `packages/agents/src/optimization/schedule.ts`
— единая точка, если позже понадобится A/B по нишам.

## Очередь

| Job kind | Режим | Назначение |
|----------|-------|------------|
| `optimization_run` | per-project | немедленный прогон после publish или точечный запуск |
| `optimization_scan` | repeatable (`OPTIMIZATION_SCAN_MS`, default 6 ч) | ищет проекты с `optimization_next_run_at <= now()` |

Переменные окружения:

- `OPTIMIZATION_SCAN_MS` — период сканера (по умолчанию `21600000` = 6 ч)
- `PIPELINE_QUEUE=inline` — jobs выполняются синхронно в процессе API (dev/test)

## Метрики в рекомендациях

Каждая рекомендация содержит `evidence` с периодом `period_from` / `period_to`
и, для CTR-просадок группы, сравнение с предыдущими 7 днями (`ctr_prior`, `ctr_current`,
`ctr_delta_pct`, `ad_group_name`). Текст rationale строится из этих цифр — LLM только
оборачивает факт, не придумывает числа.

## Ручной прогон

`POST /projects/:id/optimization/run` по-прежнему доступен — не сдвигает расписание,
если не был вызван планировщиком.

## Поля проекта (Prisma)

- `optimization_launched_at` — первая публикация кампании
- `optimization_last_run_at` — последний **успешный** автопрогон (ручной `run` это поле не трогает)
- `optimization_next_run_at` — когда сканер поставит следующий job

## Нет снапшотов в текущем окне

`runCore` требует performance snapshots в rolling-окне `optimizationComparePeriods().current`
(последние 7 суток до вчера включительно). Если окно пустое:

- **ручной** `POST .../optimization/run` → `400 Collect performance snapshots first`;
- **плановый** `runScheduled` (launch / day-7+) → прогон **пропускается**: пишется только
  новый `optimization_next_run_at`, **`optimization_last_run_at` не обновляется**
  (успешным прогон не считается). Так день-0 после publish не «сгорает», если статистика
  ещё не подтянулась.

Снапшоты собираются отдельным шагом пайплайна / sync; без них агент не выдумывает метрики.
