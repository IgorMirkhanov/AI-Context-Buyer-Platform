# Промпты для Cursor Agent

Этапы **0–17 реализованы**. Промпты 0–5 ниже — исторические (как поднимали
каркас и MVP). **Не запускайте их повторно** как задание «сделать этап».
Текущее состояние: `07_ROADMAP_MVP.md`. Живой клиент: чеклист в
`10_RISKS_AND_OPEN_QUESTIONS.md`, раздел 7.

Как пользоваться архивом: копируйте промпт только если сознательно
переписываете модуль с нуля. Перед этим `/docs` и `.cursorrules` должны
быть в корне.

Не переходите к «следующему номеру», пока предыдущий результат проверен
(для 0–17 проверка — unit + `npm run test:e2e` на моках; живой Директ —
отдельный ручной чеклист в корневом README).

```
Продолжаем "AI Context-Buyer Platform". Перед этим промптом убедись, что
уже поднят каркас из /docs/07_ROADMAP_MVP.md, Этап 0.

Изучи /docs/03_DATA_MODELS.md (таблица ad_platform_credentials и
project_briefs, JSON-схема брифа в разделе 2) и /docs/04_API_INTEGRATIONS.md

Задача (Этап 1): реализовать онбординг проекта.

Нужно:
1. Миграции для таблиц ad_platform_credentials и project_briefs по схеме
   из /docs/03_DATA_MODELS.md.
2. Модуль /packages/connectors с интерфейсом AdPlatformConnector
   (см. /docs/04_API_INTEGRATIONS.md, раздел 3) — пока с ОДНОЙ реализацией:
   [ВСТАВЬ: YandexDirectConnector / GoogleAdsConnector].
   Реализуй методы authorize() и handleOAuthCallback() полностью, остальные
   методы интерфейса (createCampaign, createAdGroups и т.д.) — как заглушки,
   бросающие NotImplementedError, мы дойдём до них на Этапе 4.

   без дизайна) с полями брифа по JSON-схеме из /docs/03_DATA_MODELS.md,

   exclusions.global_negative_keywords.
5. Кнопку "Подключить [платформа]" на странице проекта, запускающую OAuth flow.
6. Страницу проекта: статус подключения, бриф (readonly просмотр),
   кнопка "Отключить аккаунт" (удаляет токены, ставит статус disconnected).

Напиши тесты на: шифрование/расшифровку токенов, обработку OAuth callback
(с моком ответа от провайдера), валидацию брифа по JSON-схеме.

Не реализовывай агентов (Semantic Agent и далее) — это Этап 2.

## Промпт 2 — Semantic Agent

```
Продолжаем "AI Context-Buyer Platform". Этапы 0-1 из /docs/07_ROADMAP_MVP.md
уже реализованы: есть каркас, онбординг проекта и OAuth к [платформа].

Изучи /docs/05_AI_AGENTS_SPEC.md, раздел 1 (Semantic Agent) и
/docs/03_DATA_MODELS.md, раздел 3 (формат semantic_core).

Задача (Этап 2): реализовать Semantic Agent как отдельный модуль в
/packages/agents/semantic.

Нужно:
1. Миграции для таблиц semantic_keywords и semantic_clusters
   (/docs/03_DATA_MODELS.md, раздел 1).
2. Метод getKeywordIdeas в AdPlatformConnector — сначала как мок,
   возвращающий фиктивные ключевые слова с частотностью, чтобы можно было
   разработать и протестировать агента без реального доступа к
   [Wordstat / Keyword Planner]. Оформи мок так, чтобы его легко было
   заменить на реальный вызов API позже (Этап 4 или отдельная задача).
3. Пайплайн Semantic Agent по шагам из /docs/05_AI_AGENTS_SPEC.md, раздел 1:
   извлечение масок из брифа → расширение через getKeywordIdeas → разметка
   интента (hot/warm/navigational) → генерация минус-слов → кластеризация
   по эмбеддингам → финализация (удаление нулевой частотности, кросс-минусация).
4. Используй Anthropic API (Claude) для шагов, требующих LLM (извлечение
   масок, классификация интента, именование кластеров). Для кластеризации
   используй эмбеддинги + pgvector, не полагайся на LLM для группировки
   тысяч запросов целиком за один вызов.
5. Строгая JSON-схема выхода агента (semantic_core) с валидацией перед
   сохранением в БД — при несоответствии схеме статус задачи должен стать
   failed с деталями ошибки, не сохраняй частичный/некорректный результат.
6. Endpoint для запуска пайплайна на конкретном проекте + endpoint для
   просмотра результата (таблица кластеров и ключевых слов).
7. Экспорт результата в XLSX/CSV.
8. Логируй каждый вызов LLM (промпт, модель, стоимость, латентность) в
   отдельную таблицу для аудита.

Напиши тесты: на каждый шаг пайплайна отдельно (с моком LLM-вызовов),
и один интеграционный тест на весь пайплайн от брифа до semantic_core.

Не реализовывай Copywriting Agent — это Этап 3.
```

## Промпт 3 — Copywriting + Validation Agents

```
Продолжаем "AI Context-Buyer Platform". Этапы 0-2 реализованы: есть каркас,
онбординг, OAuth и Semantic Agent, выдающий semantic_core.

Изучи /docs/05_AI_AGENTS_SPEC.md, разделы 2 и 3 (Copywriting Agent и
Validation Agent) и /docs/03_DATA_MODELS.md, раздел 4 (формат ad_creatives).

Задача (Этап 3):

1. Миграция для таблицы ad_creatives (/docs/03_DATA_MODELS.md, раздел 1).
2. Справочник лимитов платформ (таблица в БД: платформа, тип элемента,
   макс. длина/количество) — не хардкодь лимиты в промптах или коде агента,
   они должны быть данными, которые можно обновить без деплоя.
3. Copywriting Agent (/packages/agents/copywriting): по каждому кластеру из
   semantic_core генерирует объявления, обязательно используя УТП из
   marketing.usp брифа, фильтруя marketing.forbidden_phrases на этапе
   генерации (в промпте), генерируя 2+ варианта на кластер для A/B.
4. Validation Agent (/packages/agents/validation): проверки лимитов
   символов/количества (детерминированный код, без LLM), кросс-минусация
   между кластерами (код), поиск запрещённых формулировок и соответствие
   forbidden_phrases (код + LLM для смысловых случаев, которые не ловятся
   простым совпадением строк), дедупликация объявлений и ключевых слов.
   Выход — список issues[] с уровнем critical/warning, часть проблем
   исправляется автоматически (обрезка длины), часть эскалируется на
   ручной просмотр в UI.
5. UI: таблица объявлений по кластерам с возможностью точечного
   редактирования текста, индикацией issues от Validation Agent.

Тесты: генерация объявлений с моком LLM (проверить, что forbidden_phrases
действительно не попадают в результат), все проверки Validation Agent как
чистые unit-тесты (без LLM, где это код), интеграционный тест
semantic_core → ad_creatives → validation issues.

Не реализовывай сборку и запуск кампании — это Этап 4.
```

## Промпт 4 — Campaign Builder и запуск кампании

```
Продолжаем "AI Context-Buyer Platform". Этапы 0-3 реализованы.

Изучи /docs/05_AI_AGENTS_SPEC.md, раздел 4 (Campaign Builder) и
/docs/03_DATA_MODELS.md, раздел 5 (единый формат структуры кампании), и
/docs/04_API_INTEGRATIONS.md полностью — сейчас нужно реализовать реальные
(не мок) методы AdPlatformConnector для [платформа].

Задача (Этап 4):

1. Миграции для campaign_drafts и campaigns.
2. Campaign Builder (/packages/agents/campaign-builder): детерминированная
   (без LLM, кроме опционального именования) сборка провалидированных
   semantic_core + ad_creatives + budget/geo из брифа в единый формат
   campaign_draft. Статус после создания: pending_approval.
3. Реализуй в YandexDirectConnector/GoogleAdsConnector (выбери
   реализованную на Этапе 1 платформу) реальные методы: createCampaign,
   createAdGroups, createAds, addKeywords, addNegativeKeywords, setBudget —
   согласно /docs/04_API_INTEGRATIONS.md. Используй официальный SDK, если
   доступен для платформы. Оберни вызовы троттлингом/ретраями с учётом
   лимитов API платформы.
4. UI подтверждения: пользователь видит campaign_draft целиком (структура,
   ключи, объявления, бюджет), может отредактировать точечно, нажимает
   "Запустить кампанию" — ТОЛЬКО после явного нажатия кнопки происходит
   вызов реальных методов создания в API платформы, и кампания создаётся
   в статусе "на паузе" (не активная), если явно не указано иное.
5. Обработка ошибок API платформы (policy violations и т.п.) — показывай
   пользователю понятную причину отказа, не проваливай весь процесс молча.

Тесты: mock-режим Connector должен продолжать работать (для тестов
пайплайна агентов), плюс отдельные integration-тесты реального Connector
на тестовом (не боевом) рекламном аккаунте — вручную, с чёткой инструкцией,
как их прогнать перед мержем.

Это первый этап, где создаются реальные объекты в кабинете. Перед тем как
я подтвержу мерж, покажи диалоговое дерево: что произойдёт при ошибке на
любом из шагов createCampaign → createAdGroups → createAds → addKeywords
(нужна ли компенсирующая логика/откат при частичном сбое).
```

## Промпт 5 — Reporting Agent

```
Продолжаем "AI Context-Buyer Platform". Этапы 0-4 реализованы, кампании
уже запускаются реально через [платформа].

Изучи /docs/05_AI_AGENTS_SPEC.md, раздел 6 (Reporting Agent) и
/docs/03_DATA_MODELS.md (performance_snapshots).

Задача (Этап 5):

1. Миграция для performance_snapshots.
2. Периодическая задача (cron/очередь), вызывающая getPerformance в
   Connector для каждого активного проекта, сохраняющая снапшоты.
3. Reporting Agent: сводка метрик за период, сравнение с target_cpl из
   брифа, 2-3 текстовых вывода на основе данных (LLM для формулировки
   выводов, но сами цифры и сравнение с целью — детерминированный код).
4. Дашборд на фронте: графики ключевых метрик по проекту, текстовая сводка
   от Reporting Agent.

Тесты: расчёт метрик и сравнение с целью — unit-тесты на конкретных числах
(без LLM), генерация текстовой сводки — с моком LLM, проверить, что цифры
в тексте совпадают с реальными посчитанными значениями (важно: агент не
должен "придумывать" цифры, только оборачивать в текст уже посчитанные).

## Как адаптировать промпты под себя

- Замените плейсхолдеры в квадратных скобках `[...]` — стек, выбранную
  платформу (Яндекс Директ / Google Ads).
- Если по ходу дела архитектура из `/docs` перестаёт соответствовать
  реальности (например, вы решили использовать другую БД), сначала
  обновите сам документ в `/docs`, а потом промпт — Cursor Agent должен
  всегда опираться на актуальную документацию, а не на память о старой версии.
- Если промпт слишком большой и Cursor Agent теряет фокус — разбейте его
  на подзадачи вручную (например, отдельно "миграции", отдельно "endpoint",
  отдельно "тесты") и подавайте по одной.
