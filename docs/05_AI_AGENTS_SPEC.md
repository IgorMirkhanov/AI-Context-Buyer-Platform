# Спецификация AI-агентов

Общий принцип: каждый агент — это узкая, проверяемая функция с чётким
входом/выходом (JSON-схема), а не "универсальный помощник". LLM внутри
агента вызывается с system-промптом, ограниченным набором инструментов
(function calling) и обязательной пост-валидацией вывода по схеме.

---

## 1. Semantic Agent (Агент семантики)

**Задача:** превратить бриф + сайт в готовое кластеризованное семантическое ядро.

**Вход:** `project_brief`, текст лендинга (краулинг), список seed-запросов (опц.).

**Пайплайн внутри агента:**
1. Извлечь маски/маркерные запросы из брифа и текста сайта (LLM-генерация +
   проверка человеком/эвристиками на здравый смысл).
2. Вызвать `getKeywordIdeas` (Wordstat / Keyword Planner через Connector Layer)
   для расширения масок в реальные пользовательские запросы с частотностью.
   **Сейчас:** для Яндекс Директа — мок Wordstat (`MockKeywordIdeasProvider`);
   для Google Ads — тот же мок. Реальный **Google Keyword Planner** — в планах:
   требует отдельной заявки на Developer Token в Google Ads API (внешний процесс,
   не блокирует MVP).
2b. **LLM-расширение по ручным seed-словам** (`suggestFromSeedWords`): если
   пользователь добавил свои слова на вкладке «Анализ», LLM предлагает
   дополнительные фразы (`source: llm_seed_expand`, в UI — «предложено ИИ»).
   Заменяет Keyword Planner для ручного ввода на текущем этапе.
2c. **План кампаний (PlanPreview)** после семантики: LLM формирует структуру
   (сколько кампаний, обоснование, группы объявлений по кластерам). Human gate
   на вкладке «План» — кнопка «Ок, собирай» запускает копирайтинг и сборку
   черновика. Черновик содержит ровно столько кампаний, сколько в утверждённом плане.
3. Разметить каждый запрос по интенту: hot / warm / navigational (LLM-классификация
   + словарные эвристики: "купить", "цена" → hot).
4. Сгенерировать список минус-слов: общие (из глобального списка проекта) +
   специфичные (LLM на основе брифа, например "дешёвый" при premium-сегменте).
5. Кластеризовать: группировка по эмбеддингам (vector similarity) + LLM-разметка
   названия кластера и категории (бренд/характеристика/гео).
6. Финализация: удалить нулевую частотность, кросс-минусация между кластерами.

**Выход:** `semantic_core` (см. `03_DATA_MODELS.md`, раздел 3).

**Инструменты:** `getKeywordIdeas`, `crawlWebsite`, embeddings API, доступ к
глобальному списку минус-слов проекта.

## 2. Copywriting Agent (Агент копирайтинга)

**Задача:** по каждому кластеру сгенерировать объявления, соответствующие
лимитам платформы и УТП из брифа.

**Вход:** `semantic_core`, `marketing` секция брифа (УТП, ЦА, стоп-слова).

**Правила генерации:**
- Обязательное использование хотя бы одного УТП из брифа в каждом объявлении.
- Соблюдение `forbidden_phrases` из брифа — фильтрация на этапе генерации,
  а не только пост-проверка.
- Генерация 2+ вариантов на кластер для последующего A/B (`ab_variants`).
- Соблюдение лимитов длины конкретной платформы (передаются как параметр,
  а не хардкодятся в промпте — платформы меняют лимиты).

**Выход:** `ad_creatives` по каждому кластеру (заголовки, описания, быстрые
ссылки, уточнения).

**Инструменты:** доступ к брифу, к справочнику лимитов платформы (таблица,
обновляемая отдельно от кода агента).

## 3. Validation Agent (Агент валидации)

**Задача:** финальный контроль качества и безопасности перед сборкой кампании.

**Проверки:**
- Соответствие лимитам символов/количества элементов платформы.
- Отсутствие `forbidden_phrases` и юридически рискованных формулировок
  (превосходная степень без доказательств: "лучший", "№1" — по правилам
  рекламных площадок).
- Кросс-минусация: ключевые слова разных групп/кампаний внутри проекта не
  конкурируют друг с другом на аукционе.
- Дубли ключевых слов и объявлений.
- Соответствие гео/языка объявления гео-таргетингу.

**Выход:** аннотированный список проблем (`issues[]` с уровнем critical/warning)
+ автоматически исправленная версия там, где исправление однозначно
(например, обрезка текста до лимита), и явная эскалация человеку там, где
неоднозначно (например, потенциально рискованная формулировка).

**Важно:** этот агент — не творческий, а детерминированный по максимуму:
где возможно, использовать обычный код/regex/справочники вместо LLM,
LLM — только для смысловых проверок (соответствие УТП, тон).

## 4. Campaign Builder Agent

**Задача:** собрать финальную структуру кампании из провалидированных
семантики и объявлений в единый внутренний формат (см. `03_DATA_MODELS.md`,
раздел 5), готовый к передаче в `Connector Layer`.

**Вход:** `semantic_core` (после валидации), `ad_creatives` (после валидации),
секция `project.budget`/`geo`/`platforms` из брифа.

**Логика:** в основном детерминированная сборка (код, не LLM) — маппинг
кластеров в группы объявлений, применение бюджета и таргетингов из брифа.
LLM может использоваться точечно для именования кампаний/групп в читаемом виде.

**Выход:** `campaign_draft` (статус `pending_approval`).

## 5. Optimization Agent

**Задача:** по `performance_snapshots` и wasted search terms предлагать
`pause_campaign` / `reduce_budget` / `add_negative`. Реализован (этап 7).

**Расписание (фоновые job):** день 0 после publish, день 7, далее каждые 7 дней —
см. `docs/13_OPTIMIZATION_SCHEDULE.md`. Очередь: `optimization_scan` +
`optimization_run` (BullMQ / inline). Ручной `POST .../optimization/run` не
сдвигает расписание.

Агент **предлагает** действие со ссылкой на цифры (`evidence_json` +
`rationale`, период `period_from`–`period_to`, для CTR-просадок группы —
`ctr_prior` / `ctr_current` / `ctr_delta_pct`). В кабинет — после «Принять» и
«Применить», либо автопилот (этап 11) после порога. Новые кампании автопилот не
создаёт.

## 6. Reporting Agent

**Задача:** превратить сырые `performance_snapshots` в человекочитаемый отчёт
с выводами, а не просто таблицу цифр.

**Вход:** метрики за период, цели из брифа (`target_cpl`).

**Выход:** структурированный отчёт: ключевые метрики, сравнение с целью
(`target_cpl` vs факт), 2-3 главных вывода (Reporting Agent). Optimization
подключается отдельной кнопкой, не внутри отчёта.

---

## 7. Orchestrator (не совсем "агент", но управляет остальными)

**Задача:** детерминированно вести проект по стадиям, вызывать агентов в
правильном порядке, обрабатывать ошибки, не позволять LLM самому решать
"что делать дальше" на уровне всего пайплайна (это должно быть управляемо
кодом/state machine, LLM работает только внутри шагов).

**Состояния проекта:** `brief_submitted → semantic_in_progress →
semantic_ready → copywriting_in_progress → copy_ready →
validation_in_progress → draft_ready → awaiting_approval →
launched → live_optimizing`.

## 8. Общие требования ко всем агентам

- Каждый вызов LLM логируется (промпт, модель, стоимость, латентность) для
  аудита и оптимизации расходов.
- Вывод каждого агента строго валидируется по JSON-схеме перед сохранением
  в БД — при несоответствии схема-ошибке задача уходит в статус `failed`
  с деталями, а не сохраняет "почти правильный" результат.
- Промпты хранятся вне кода как отдельные версионируемые файлы/записи в БД —
  чтобы их можно было менять и A/B-тестировать без деплоя.
