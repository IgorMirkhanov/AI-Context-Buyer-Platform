# Semantic Agent — регрессионный QA и baseline

Диагностика смысловой корректности ядра, отдельно от метрики `quality`
(доля объявлений/кластеров без ручной правки). Это **не** Playwright и
**не** unit-тест с порогом pass/fail: контекстолог смотрит цифры и списки
расхождений.

Запуск (мок Wordstat + `HeuristicSemanticLlm`, без кабинета и без LLM API):

```
npm run qa:semantic
```

Эталоны: `qa/semantic/fixtures/*.json`. Сравнение: `packages/agents/src/semantic/qa-compare.ts`.

## Откуда эталоны (не от LLM)

Новых ключей модель не сочиняла. Пять фикстур:

| id | Бриф | Ключи эталона |
|----|------|----------------|
| `asus-gaming` | `semantic-pipeline.spec.ts` | фразы из `docs/03_DATA_MODELS.md` §3 + фразы spec + шаблоны `MockKeywordIdeasProvider` на человеческий УТП |
| `asus-hp-brands` | имена кластеров из `copywriting-pipeline.spec.ts` / `campaign-builder.spec.ts` | `купить asus rog`, `купить hp omen` и шаблоны мока на эти две строки |
| `office-laptops` | поля формы `e2e/platform.spec.ts` | точная строка УТП + шаблоны мока на неё |
| `orthodontics-clinic` | **свежий бриф** (B2C-медуслуги, СПб) | шаблоны мока на два УТП + 4 ручные коммерческие формулировки |
| `accounting-b2b` | **свежий бриф** (B2B-услуги, аутсорсинг учёта) | шаблоны мока на два УТП + 4 ручные коммерческие формулировки |

У каждой фразы в JSON есть поле `source`. Расширять эталон нужно вручную
(добавить ключ в `gold` или правило в `irrelevant`), а не генерировать
«идеальное ядро» чатом.

Разовая разметка мусора (`irrelevant`): сервисный шаблон `{seed} ремонт`
из мока Wordstat, минусы брифа (`бесплатно`, `скачать`, `торрент`), сегмент
ЦА как запрос, хост `website_url` как маска.

## Метрики

- **Покрытие (recall)** — какая доля эталонных ключей нашлась у агента
  (нормализация: trim, нижний регистр, схлопывание пробелов).
- **Точность (precision)** — `1 − (размеченный мусор / все ключи агента)`.
  В штраф идут только правила `irrelevant`. Фразы «не в эталоне и ещё не
  размечены» печатаются списком и **не** портят precision, пока их не
  перенесут в gold или irrelevant.
- **Разделение кластеров** — среднее косинусное сходство (те же
  hash-n-gram эмбеддинги, что у агента) внутри кластера минус среднее
  сходство случайных пар из разных кластеров. Выше — лучше отделение.

### Контрольный эталон `orthodontics-clinic` (2026-08-28)

Свежая ниша без пересечения с ноутбуками/asus/rog. Прогон показывает:

- **Шаблоны мока на УТП — 14/14 (100%)**: агент стабильно разворачивает
  `{seed}` → `купить/цена/обзор/…` на любой бриф, не только на три
  «выученных» фикстуры.
- **Ручные коммерческие формулировки — 0/4**: не найдены
  `брекеты для взрослых`, `лечение кариеса цена`, `стоимость установки
  брекетов`, `записаться на брекеты` — для ортодонтии нет производных масок
  (нет сингуляра/бренда/линейки), мок не генерирует синонимы.
- **Precision 100%** — фильтр минусов и отсутствие шумных масок ЦА/хоста
  работают и вне электроники.
- **Разделение кластеров 0.42** — два УТП остаются в разных кластерах
  (по 7 ключей), схлопывания нет.

Итог: рост recall на `asus-gaming` — не «зазубривание трёх ответов», но
**обобщение на мок-шаблоны ограничено**: без доработки масок/мока в новой
нише теряется recall на человеческих коротких запросах.

## Эвристики масок vs LLM: оценка (2026-08-28)

### Почему дальше не расширять `deriveMasksFromUsp`

Пропущенные ключи на двух контрольных нишах — **лексическая вариативность
intent**, а не недостающая маска:

- глагольный CTA (`записаться на`, `передать учет на`) ≠ шаблон `купить {seed}`
- разговорный синоним (`сколько стоит`, `стоимость`) ≠ `{seed} цена`
- укороченное ядро (`лечение кариеса цена`) ≠ полное УТП + `цена`
- ролевая формулировка (`бухгалтер для ип`) ≠ существительное из УТП

Добавление правил под эти 8 фраз — продолжение пути `asus`/`rog`: recall
растёт на конкретных эталонах, но каждое правило — потенциальный шум в
другой вертикали. На `accounting-b2b` текущие эвристики уже дают побочную
маску `аутсорсинг для ип` (отрезание прилагательного `бухгалтерский`) —
7 лишних ключей в `unlabeledExtras`, **0** из 4 пропущенных near-intent.

**Вывод: дальнейшее расширение масок эвристиками нереалистично** как
универсальное решение near-intent recall.

### Рекомендуемый источник: LLM-подсказки поверх Wordstat

| Аспект | Baseline (без ключа) | Production (с ключом Anthropic) |
|--------|----------------------|----------------------------------|
| Маски | `HeuristicSemanticLlm.extractMasks` → `masksFromBrief` | `AnthropicSemanticLlm` объединяет LLM-маски с heuristic baseline |
| Расширение | только `getKeywordIdeas(masks)` | **+** `suggestNearIntentPhrases(brief, wordstatKeys)` |
| Провайдер | `npm run qa:semantic` — всегда heuristic | `SemanticService` → `resolveSemanticLlm()` → `AnthropicSemanticLlm` при `AiProviderService.tryResolveOptional` |
| Деградация | — | нет ключа → `HeuristicSemanticLlm` + **явный warn** в лог (`SEMANTIC_HEURISTIC_FALLBACK_MESSAGE`), не тихая подмена |

Место в пайплайне (`packages/agents/src/semantic/pipeline.ts`, после `filterKeywordsStep`):

```
Wordstat(masks) → filter → [LLM: near-intent фразы] → re-filter → labelIntent → cluster
```

Реализация (2026-08-31):

- `packages/agents/src/semantic/anthropic-llm.ts` — `AnthropicSemanticLlm` (интерфейс `SemanticLlm`)
- `packages/agents/src/semantic/resolve-llm.ts` — выбор LLM по наличию ключа
- `apps/api/src/semantic/semantic.service.ts` — `tryResolveOptional` + `llmMode` в ответе
- Подсказки near-intent: `source: llm_near_intent`, `frequency: 1`; повторный `filterKeywordsStep`
  отсекает минусы и дубли
- При ошибке Anthropic API отдельные шаги LLM деградируют на heuristic внутри `AnthropicSemanticLlm`

**Baseline QA не меняется:** `npm run qa:semantic` по-прежнему гоняет
`HeuristicSemanticLlm` + `MockKeywordIdeasProvider` — это законный сценарий
«организация без ИИ-провайдера».

| **Reporting** | **нет** | `apps/api/src/reports/reports.service.ts` | `HeuristicReportingLlm` (вне scope задачи, для полноты) |

### Validation Agent: осознанно rule-based

**Решение:** Validation **не переводится на LLM**. Это формальная пост-проверка
ограничений платформы (длины, forbidden, дубли, cross-minus), а не творческая
задача. LLM здесь добавил бы недетерминизм и риск «пропустить» критическое
нарушение; правила в `validateCreatives` воспроизводимы в unit-тестах и
совпадают с политикой модерации площадок.

Copywriting Agent генерирует тексты (LLM или heuristic), Validation Agent
только проверяет результат — отдельная запись `AgentType.validation` в
`creatives.service.ts` фиксирует факт прогона валидатора, без `llmMode`.

Полный пайплайн (`apps/api/src/pipeline/pipeline.service.ts`) по-прежнему вызывает
`requireReady` — отдельные агенты (semantic, copywriting, optimization) могут
работать в heuristic-режиме без ключа, но цепочка агентов требует настроенный
ИИ-провайдер.

Предыдущий baseline (до правок):

| Фикстура | Recall | Precision | Intra − inter | Эталон / агент |
|----------|--------|-----------|---------------|----------------|
| asus-gaming | 58.3% (7/12) | 43.8% (мусор 18/32) | 0.4031 | 12 / 32 |
| asus-hp-brands | 100% (10/10) | 43.8% (мусор 18/32) | 0.3635 | 10 / 32 |
| office-laptops | 100% (7/7) | 29.2% (мусор 17/24) | 0.4132 | 7 / 24 |

Что исправлено относительно предыдущего baseline:

1. **Recall asus-gaming 58% → 100%** — производные маски из УТП (`игровой
   ноутбук asus`, `ноутбук asus`, `asus`, `asus rog`) дают моку нужные seed'ы
   для эталонных фраз spec и docs/03.
2. **Precision 29–44% → 100%** — убраны маски ЦА и хоста; ключи с `ремонт`
   и глобальными минусами фильтруются до кластеризации.
3. **Кластеры** — см. раздел «Кластеризация: отделение intent-хвостов»;
   фикс `phraseClusteringCore` разнёс бренды на asus-фикстурах без
   просадки `orthodontics-clinic` (0.4225).

## Кластеризация: отделение intent-хвостов от продуктового ядра (2026-08-28)

### Проблема

Hash-n-gram эмбеддинги считались по **полной фразе**. Шаблоны мока добавляют
общие хвосты (`официальный сайт`, `обзор`, `отзывы`, `цена`), из‑за чего
кластеризовался **intent**, а не продукт: на `asus-hp-brands` в один кластер
попадали `asus rog официальный сайт` и `hp omen официальный сайт`; на
`asus-gaming` — `гарантия 3 года официальный сайт` вместе с asus-линейкой.

### Рассмотренные варианты

| Вариант | Суть | Итог прогона |
|---------|------|--------------|
| **A. Продуктовое ядро в эмбеддинге** | Перед `embed()` снять префикс `купить` и хвосты intent-модификаторов (`phraseClusteringCore`) | **Принят** — см. таблицу ниже |
| **B. Раздельная кластеризация hot vs warm/nav** | Сначала commercial (`hot`), затем warm/navigational по тому же ядру | Отклонён: метрика intra−inter просела сильнее; на `asus-gaming` warm-ключи снова слиплись в один мегакластер |

### Реализация (вариант A)

`packages/agents/src/semantic/heuristics.ts` — `phraseClusteringCore()`:
снимает `купить ` и хвосты `официальный сайт` / `отзывы` / `обзор` /
`цена` / `заказать` **только для векторизации**, intent на ключе (`hot` /
`warm` / `navigational`) **не меняется**.

`clusterStep` эмбеддит `phraseClusteringCore(phrase)`, а не сырую строку.

**Осознанное архитектурное решение:** navigational и warm остаются в тех же
кластерах, что и commercial с тем же продуктовым ядром (одна ad group на
продукт), но группировка определяется **ядром УТП/маски**, а не общим
хвостом шаблона Wordstat. Это не заплатка под asus, а правило уровня
пайплайна: «кластеризуем по продукту, intent — атрибут ключа».

### Метрики intra−inter до / после (вариант A)

| Фикстура | До (полная фраза) | После (`phraseClusteringCore`) | Цель |
|----------|-------------------|--------------------------------|------|
| asus-gaming | 0.2094 (inter 0.49) | **0.2361** (inter **0.38**) | исправить смешение брендов/УТП |
| asus-hp-brands | 0.2886 (inter 0.31) | **0.2743** (inter **0.27**) | разнести asus vs hp |
| orthodontics-clinic | **0.4225** | **0.4225** | не просадить |
| accounting-b2b | 0.4862 | **0.4862** | без регрессии |
| office-laptops | — | — | без изменений (1 кластер) |

### Состав кластеров после фикса (глазами)

**asus-hp-brands** — 3 кластера, **hp omen не в кластере asus rog**:
- `asus rog` + производные asus (14)
- `rog` (7)
- `hp omen` + omen (14)

**asus-gaming** — 2 кластера, **гарантия отделена от asus-линейки**:

## Падение intra−inter на `asus-gaming` (историческая диагностика)

Метрика упала почти целиком за счёт роста **inter** (0.38 → 0.49), а не
падения intra (0.79 → 0.70). То есть кластеры стали **ближе друг к другу**,
а не «кучнее внутри».

### До правок (4 кластера × 8 ключей, 32 всего)

| Кластер (маска-источник) | Примеры ключей |
|--------------------------|----------------|
| `игровые ноутбуки asus` | USP + шаблоны мока |
| `гарантия 3 года` | второе УТП + шаблоны |
| `геймеры 18-30` | сегмент ЦА (шум) |
| `asus-gaming` | хост домена (шум) |

Кластеры однородны: внутри семьи общий длинный префикс seed, между семьями
пересечений мало → высокий inter-gap.

### После правок (6 кластеров, 49 ключей)

| Кластер агента | Размер | Что внутри (проблемные смешения **жирным**) |
|----------------|--------|---------------------------------------------|
| `игровые ноутбуки asus` | **26** | Все варианты USP + производные (`игровой ноутбук asus`, `ноутбук asus`); **плюс** `asus обзор`, `asus rog официальный сайт`, `ноутбук asus rog официальный сайт`, **`гарантия 3 года официальный сайт`** |
| `asus` | 11 | Маска `asus` / `asus rog`: бренд и линейка |
| `купить asus` | 2 | Фрагмент по префиксу intent |
| `asus заказать` | 2 | То же |
| `asus отзывы` | 2 | То же |
| `гарантия 3 года` | 6 | Второе УТП (без навиг. хвоста, уехавшего в мегакластер) |

**Исторически (до фикса кластеризации):** это была склейка по общему хвосту
`официальный сайт`. См. раздел «Кластеризация: отделение intent-хвостов» —
